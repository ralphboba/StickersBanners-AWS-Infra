# 레거시(Linh) 프로그램과의 충돌 감사

요구: **두 프로그램이 서로에게 영향을 주면 안 된다.** Linh의 SBBotExpress는 지금도
실제 주문을 처리하고 있고, 우리 업그레이드 기능은 같은 OrderDesk 스토어를 건드린다.

공유하는 자원을 하나씩 세어보고, 각각 어떻게 격리했는지 기록한다.

## 공유 자원 목록

| # | 공유하는 것 | 위험 | 상태 |
| --- | --- | --- | --- |
| C1 | OrderDesk **QTS 폴더** (레거시의 입력 큐) | 유령 주문 유입 | ⚠️ **확인 필요** |
| C2 | **익스프레스 컷오프** 업그레이드 | 무료로 줄 것을 유료로 판매 | ✅ 코드로 차단 |
| C3 | 같은 주문에 대한 **PUT** | lost update | ⚠️ 완화만 가능 |
| C4 | OrderDesk **API rate limit** | 레거시가 429로 멈춤 | ✅ 요청량 동결 |
| C5 | `shipping_method` **문자열 표기** | 같은 서비스가 두 표기로 갈림 | ✅ 레거시에 맞춤 |
| C6 | **폴더 이동** (레거시의 상태 기계) | 상태 기계 파손 | ✅ 우리는 안 옮김 |
| C7 | `order_notes` | 누적 | 🟢 경미 |

## C1 — 유령 주문이 레거시의 큐로 들어간다 ⚠️ 최대 위험

초안 주문 D###가 결제되면 **Shopify에 진짜 주문이 하나 생긴다.** 그러면:

```
D169 결제 → Shopify 주문 생성 → OrderDesk가 신규 주문으로 다운로드
   → 인테이크 Lambda가 getDestinationFolder로 QTS(665685)에 넣음
   → ★ 레거시 봇이 이걸 집어서 생산하려 한다
   → 아트워크가 없다 → 게이트가 Red/manual로 분류
   → 스태프 큐에 "파일 없는 주문"이 쌓이는데 실은 배송비다
```

**이건 우리 대시보드 문제가 아니라 Linh 프로그램의 입력이 오염되는 문제다.**

### 막는 법 (셋 중 하나, 확인 후 결정)

1. **OrderDesk 다운로드 필터** — 연동 설정에서 초안 유래 주문을 안 받게 한다. 있으면 최선
2. **인테이크 Lambda에서 차단** — `getDestinationFolder`가 `D`로 시작하는 주문명이나
   "Shipping Upgrade" 라인만 있는 주문을 보면 QTS가 아닌 전용 폴더로 보낸다
3. **우리가 즉시 치운다** — `orders/paid` 직후 D###를 전용 폴더로 이동

> **선행 확인:** 테스트 초안 1건을 만들어 결제하고, 5분 뒤 OrderDesk QTS를 본다.
> **이 확인 전에는 SHOPIFY_WRITES를 켜면 안 된다.**

## C2 — 익스프레스 이중 업그레이드 ✅ 차단함

레거시 `changeExpress`(우리 `routing.mjs` 136행): **3-day 주문이 3–6pm ET에 라우팅되면
무료로 2-day가 된다.**

우리 사다리도 3-Day → 2-Day를 판다. 겹치면 **고객이 공짜로 받을 걸 돈 내고 산다.**

### 어떻게 막았나 — 시계가 아니라 폴더로

```js
const routed = Boolean(folder?.facility);
const legacyMayUpgradeFree = ladder?.from === '3-day Shipping' && !routed;
```

주문이 아직 시설 폴더에 없으면 레거시가 무료 업그레이드를 할지 알 수 없다 → **3-Day
업그레이드를 아예 안 보여준다.** 시설 폴더에 들어갔는데도 여전히 3-day면 레거시가 이미
"안 올린다"고 판단한 것이므로 그때는 우리가 팔아도 된다.

**시각을 보지 않는다.** 3–6pm으로 판정하면 "지금은 4시가 아니지만 라우팅은 4시에 될
주문"을 놓친다. 폴더 기준은 언제 열어도 맞다.

2-Day → 1-Day는 영향 없다. 레거시는 1-day를 무료로 주지 않는다.

## C3 — PUT 경합 ⚠️ 완화만 가능

레거시도 우리도 주문 레코드 **전체**를 PUT한다. OrderDesk에는 낙관적 락이 없으므로
동시에 쓰면 나중 것이 앞 것을 덮는다.

완전 제거는 불가능하다. 창을 줄인다:

- PUT **직전에** 재조회해서 변경 필드만 병합 — `applyShippingUpgrade`는 ✅ 이렇게 한다.
  `applyExpressUpgrade`(레거시 포팅)는 아직 아니다
- 우리 쓰기는 **주문당 평생 1회**다 (업그레이드는 한 번뿐). 레거시는 인테이크에서 몇 번
  쓰는데, 그 구간엔 우리가 아예 안 쓴다(C2 가드가 미라우팅 주문을 막으므로)

**실질적으로 두 프로그램이 같은 주문에 동시에 쓰는 창이 거의 없다** — 레거시는 인테이크,
우리는 생산 중. C2 가드가 그 분리를 강제한다.

## C4 — rate limit ✅ 요청량을 동결했다

미러가 폴더 10개 → **20개**로 늘었다(생산·Awaiting Shipment 추가). 같은 스토어를 레거시도
폴링하므로 예산을 나눠 쓴다. **우리가 늘리면 레거시가 429를 맞을 수 있다.**

→ **미러 주기를 5분 → 10분으로 늘렸다.** 요청량이 정확히 이전과 같아진다:

```
전:  10 폴더 / 5분  = 분당 2회
후:  20 폴더 / 10분 = 분당 2회
```

대가는 스태프 보드가 최대 10분 늦는 것. **돈이 걸린 경로는 미러를 안 쓴다** — 결제 직전에
OrderDesk를 직접 읽는다(주문당 1회).

> **더 나은 격리:** OrderDesk가 rate limit을 **키 단위**로 건다면, 우리 전용 API 키를
> 발급받으면 완전히 분리된다. 스토어 단위라면 위 동결이 유일한 방법이다. **확인 필요.**

## C5 — `shipping_method` 표기 ⚠️ 레거시 쪽이 틀렸다

실제 스토어가 쓰는 값 (Kai 확인, 2026-09-14):

```
FedEx Ground · FedEx 3-Days · FedEx 2-Days · FedEx 1-Day
```

우리 사다리는 이 넷을 그대로 쓴다. ✅

**그런데 `routing.mjs`의 레거시 익스프레스 업그레이드는 `'2-day Shipping'`을 쓴다 —
넷 중 아무것도 아니다.**

| | 쓰는 값 | 스토어가 아는가 |
| --- | --- | --- |
| 우리 업그레이드 | `FedEx 1-Day` | ✅ |
| 레거시 익스프레스 (`routing.mjs`) | `2-day Shipping` | ❌ |

`ORDERDESK_WRITES`가 꺼져 있어서 **아직 실제로 쓰인 적은 없다.** 하지만 인테이크를
go-live하는 순간 3-day 주문이 컷오프에 걸릴 때마다 인식 불가능한 서비스명이 박히고,
ShipStation 매핑이 그걸 못 찾는다.

> **인테이크 go-live 전 필수 수정.** 우리 업그레이드 기능과는 무관하므로 이 기능을
> 막지는 않는다. 다만 Linh 확인 대상인지 판단이 필요하다 — 레거시 동작을 바꾸는 게
> 아니라 **레거시가 의도한 대로 되게 하는 수정**으로 보인다.

---

## C6 — 폴더 이동 ✅ 우리는 안 옮긴다

레거시의 상태 기계는 폴더다. 폴더를 옮기면 레거시가 다르게 행동한다.

Kai의 사다리 규칙("기존 생산팀 유지")이 우리를 여기서 완전히 빼놨다. **업그레이드는
`shipping_method` 하나만 쓴다.** 폴더 이동도, 재라우팅도 없다.

`ORDERDESK_WRITES`(인테이크 게이트의 폴더 이동)는 계속 꺼져 있다 — 지금 가장 강한
안전장치다. **주문을 옮기는 주체는 레거시 하나뿐이다.**

## C7 — 노트 누적 🟢 경미

업그레이드마다 노트가 한 줄 붙는다. 인테이크 Lambda의 멱등성 검사가 노트를 스캔하므로
길어지면 아주 조금 느려진다. 주문당 1회라 실질 영향은 없다.
